\chapter{Introduction}

Although most embedded software developers recognize the importance of strong
typing, as a tool to write more reliable software, many get discouraged of
using Ada, the strongest-typed language there is, just because of its syntactic
verbosity, or perhaps simply because Ada does not look more like C.

What if we could have a new programming language for embedded software that looks
like C but has an Ada soul, that is, a language with all the Ada concepts but
in a C skin, C with a strongly-typed armor, and where using pointers is more
the exception than the norm.

This document presents \emph{stC} (\emph{Strongly-Typed C}), a programming language
for safety-critical embedded software development.

A proof-of-concept compiler for \emph{stC}, known as \verb'stcc', has been written
in Ada 2022. It acts as a transpiler that translates \emph{stC} source code into
SPARK Ada 2022 \cite{SparkAda} source code that can be formally verified with GNATprove.
The code of \verb'stcc' is available in GitHub at \url{https://github.com/jgrivera67/stcc}.

\section{Language Overview}

The main goal of \emph{stC} is to make the timeless safe and secure software engineering principles of
Ada/SPARK more accessible and apealing to embedded C software developers, by presenting them in the more
familiar C syntax.
The language enforces strong typing, supports design-by-contract, and transpiles to SPARK Ada
so that the full power of GNATprove formal verification is available to every \emph{stC} programmer.

\begin{itemize}

\item \emph{stC} is a fully strongly-typed language. There is no automatic integer promotion
 or any other implicit type conversions.

\item There are no built-in integer types in \emph{stC}. All integer types must be explicitly declared,
using language constructs to define range-based or modular-based integer types. The only built-in
types are \verb'bool' and \verb'char'.

\item Unlike C, \emph{stC} allows the programmer to write completely pointer-free code in general.
      No explicit pointers are needed for ordinary data structures, and because the language does not
      support dynamic memory allocation, pointers are not needed for heap management either.
      Using pointers is the exception, not the norm.

\item \emph{stC} provides programming-by-contract constructs.
      Function contracts --- preconditions (\verb'[[pre]]'), postconditions (\verb'[[post]]'),
      and type invariants (\verb'[[type_invariant]]') --- are part of the signature of a function
      or type declaration, not just comments.
      Loop contracts --- loop invariants (\verb'[[loop_invariant]]') and loop variants
      (\verb'[[loop_variant]]') --- can be attached to any loop to prove termination and
      absence of runtime errors within the loop body.
      Data-flow contracts --- global variable clauses (\verb'[[global]]') and information-flow
      dependencies (\verb'[[depends]]') --- precisely capture which state a function reads or
      writes and how each output depends on the inputs.
      Because the transpiler emits all contracts as SPARK aspects, they are statically provable
      by GNATprove.

\item Precise bit-level representation of hardware registers can be specified as part of
      the corresponding struct declarations, using \verb'[[at]]', \verb'[[offset]]',
      \verb'[[bits]]', and \verb'[[volatile]]' attributes.
      This makes safe MMIO register access straightforward, without raw pointer casts or
      fragile \verb'volatile' structs.

\item Types can be qualified with logical predicates to support ``liquid types''
      (\emph{logically qualified} types).

\item Arrays cannot implicitly be treated as pointers and they carry their length when
      passed as parameters to functions.

\item There are no header files and no preprocessor.

\item Declarations can be in any order. Symbols can be used before they are declared.
      In \emph{stC} there is no need for function prototypes or forward declarations.

\item A module has an explicit name specified at the beginning of the source file with the
      \verb'module' keyword.

\item A module can import declarations from other modules using their names.
      An import can be prefixed with \verb'private' (analogous to Ada's \verb'private with'),
      meaning the imported module is only usable within the current module's private section.

\item A module can have private declarations that are not visible to other modules.

\item A module can have child modules. A child module is
      named by using its parent module's name followed by a dot as a prefix.

\item A child module inherits all the public and private declarations of its ancestor modules.
      However, inherited private declarations cannot be used in the visible parts of the module's public
      declarations.

\item A parent module can access its child modules' public declarations without an explicit
      \verb'import'.  Combined with the rule above, parent--child module name resolution is
      \emph{bidirectional}: children inherit parent declarations, and parents can reference
      child declarations.  The \verb'import' statement is only needed for unrelated modules
      and for sibling modules within the same module family.

\item A child module can be declared \emph{private} by prefixing its \verb'module' declaration with the
      \verb'private' keyword.  A private child module is only accessible to its parent module and to
      sibling modules within the same module family; it cannot be imported by unrelated modules.
      This corresponds to Ada's \emph{private child package} concept.

\item The language is case-sensitive. All reserved words are lower case.

\item The language is block-structured. Blocks are delimited by curly braces.

\end{itemize}

\section{stcc}
\verb'stcc' is implemented in Ada 2022 and acts as a transpiler: it translates \emph{stC}
source files into equivalent SPARK Ada 2022 source code. The generated code is intended to
be fully compilable with GNAT and formally verifiable with GNATprove \cite{SparkAda}.

\begin{itemize}
\item For each \emph{stC} file an Ada package specification file (\verb'.ads') and an Ada package
body file (\verb'.adb') are generated. To compile these files with the GNAT compiler, the \verb'-gnatX' flag
must be used, to enable the curated subset of GNAT language extensions, which are used in the generated
files \cite{gnatX}.

\item Line number form the original \emph{stC} source file are included as end-of-line comments
in the generated Ada code.
\end{itemize}

\chapter{Lexical Elements}

\section{Tokens}
The lexical structure of \emph{stC} consists of the following token types:
\begin{itemize}
\item Keywords (reserved words)
\item Identifiers
\item Literals (integer, floating-point, character, string, boolean)
\item Operators
\item Punctuation symbols
\item Comments
\end{itemize}

\section{Keywords}
The following identifiers are reserved as keywords and cannot be used as identifiers:

\begin{lstlisting}
abstract_state  as              assert          auto            bit
bits            bool            break           case            char
compile_if      const           continue        decimal         default
delta           depends         digits          do              else
enum            extern          false           first           fixed

goto            if              import          in              inout
last            loop_invariant  loop_variant    modular         module

return          size            sizeof          static          struct

\end{lstlisting}

Note: \verb'machine_width' is not a keyword but a built-in constant (see section on Built-in Constants).

\section{Identifiers}
An identifier consists of a letter followed by zero or more letters, digits, or underscores:
\begin{lstlisting}
identifier   = letter (letter | digit | '_')*
letter       = 'a'..'z' | 'A'..'Z'
digit        = '0'..'9'
\end{lstlisting}

Identifiers are case-sensitive. Examples: \verb'myVariable', \verb'Count_1', \verb'MAX_SIZE'

\section{Literals}

\subsection{Integer Literals}
\emph{stC} supports three integer literal formats:
\begin{itemize}
\item \textbf{Decimal}: \verb'0', \verb'42', \verb'1234', \verb'1_000_000'
\item \textbf{Hexadecimal}: \verb'0x0', \verb'0x2A', \verb'0x4D2', \verb'0xDEAD_BEEF', \verb'0x8000_0000'
\item \textbf{Binary}: \verb'0b0', \verb'0b101010', \verb'0b1111_1111', \verb'0b1010_0101'
\end{itemize}

Both underscores (\verb'_') and apostrophes (\verb''') can be used as digit separators to improve readability. Apostrophes are supported for compatibility with C.

Separators are allowed between digits but not at the beginning or end of a number, and not immediately after the base prefix (\verb'0x' or \verb'0b'). A literal must use only one separator style - mixing \verb'_' and \verb''' in the same literal is an error.

\textbf{Examples:}
\begin{lstlisting}
1_000_000        // Decimal with underscores
1'000'000        // Decimal with apostrophes (C compatibility)
0xDEAD_BEEF      // Hexadecimal with underscores
0xDEAD'BEEF      // Hexadecimal with apostrophes
0b1111_1111      // Binary with underscores
0b1111'1111      // Binary with apostrophes

// Invalid examples
// 0x8000_0'000   // Error: mixed separators
// 1000_          // Error: trailing separator
\end{lstlisting}

\subsection{Floating-Point Literals}
Floating-point literals have the form:
\begin{lstlisting}
3.14
2.71828
1.0e10
6.022e23
\end{lstlisting}

\subsection{Character Literals}
Character literals are enclosed in single quotes:
\begin{lstlisting}
'a'  'Z'  '0'  '\n'  '\t'  '\\'  '\''
\end{lstlisting}

Escape sequences:
\begin{itemize}
\item \verb'\n' -- newline
\item \verb'\t' -- tab
\item \verb'\r' -- carriage return
\item \verb'\\' -- backslash
\item \verb'\'' -- single quote
\item \verb'\"' -- double quote
\item \verb'\0' -- null character
\end{itemize}

\subsection{String Literals}
String literals are enclosed in double quotes:
\begin{lstlisting}
"Hello, World!"
"Line 1\nLine 2"
"Path: C:\\Users\\name"
\end{lstlisting}

\section{Scalar Types}

\subsection{Range Types}

Range types define integer types with explicit minimum and maximum bounds. The compiler enforces these bounds, and runtime checks can verify that values stay within range.

\textbf{Syntax:}
\begin{lstlisting}
type range <min-expr> .. <max-expr> <type-name>;
\end{lstlisting}

\textbf{Examples:}
\begin{lstlisting}
// Integer types based on ranges
type range 0 .. 255 byte_t;
type range 0 .. 100 percentage_t;
type range -273 .. 1000 temperature_t;
type range -32768 .. 32767 int16_t;

percentage_t cpu_usage = 75;
temperature_t room_temp = 22;
\end{lstlisting}

Range types are ideal for:
\begin{itemize}
\item Values with natural limits (percentages, temperatures, indices)
\item Representing subsets of integers with specific meaning
\item Enabling compiler optimizations based on known bounds
\end{itemize}

\subsection{Modular Types}

Modular types define unsigned integer types with wraparound arithmetic modulo a specified value. When a value exceeds the modulus, it wraps around to zero. Modular types are perfect for implementing C-style unsigned integers and bit manipulation.

\textbf{Syntax:}
\begin{lstlisting}
type modular <modulus-expr> <type-name>;
\end{lstlisting}

The modulus defines the range \verb'[0, modulus-1]'. Arithmetic operations wrap around automatically.

\textbf{Defining C Standard Unsigned Integer Types:}

\emph{stC} provides multiple equivalent ways to define standard unsigned integer types. You can use decimal literals, bit shift expressions, or exponentiation:

\begin{lstlisting}
// uint8_t: 8-bit unsigned (0..255)
type modular 256 uint8_t;      // Using decimal literal
type modular 1 << 8 uint8_t    // Using bit shift
type modular 2 ** 8 uint8_t;   // Using exponentiation

// uint16_t: 16-bit unsigned (0..65535)
type modular 65_536 uint16_t;  // Using decimal literal
type modular 1 << 16 uint16_t; // Using bit shift
type modular 2 ** 16 uint16_t; // Using exponentiation

// uint32_t: 32-bit unsigned (0..4294967295)
type modular 4_294_967_296 uint32_t; // Using decimal literal
type modular 1 << 32 uint32_t;       // Using bit shift
type modular 2 ** 32 uint32_t;       // Using exponentiation

// uint64_t: 64-bit unsigned (0..18446744073709551615)
type modular 1 << 64 uint64_t;    // Using bit shift (most readable)
type modular 2 ** 64 uint64_t;    // Using exponentiation
\end{lstlisting}

\textbf{Wraparound Behavior:}
\begin{lstlisting}
uint8_t counter = 255;
counter = counter + 1;  // Wraps to 0

uint8_t value = 0;
value = value - 1;      // Wraps to 255
\end{lstlisting}

Modular types are ideal for:
\begin{itemize}
\item Bit manipulation and bitwise operations
\item Hardware register access
\item Cryptography and checksums
\item Circular buffers and wraparound counters
\item Compatibility with C unsigned integer types
\end{itemize}

\subsection{Floating Point Types}

Floating point types define real number types with specified decimal precision. They are similar to Ada floating point types and provide approximate representation of real numbers.

\textbf{Syntax:}
\begin{lstlisting}
type float digits <precision> <type-name>;
type float digits <precision> range <min> .. <max> <type-name>;
\end{lstlisting}

The \verb'digits' clause specifies the minimum number of decimal digits of precision. An optional \verb'range' clause constrains the valid values.

\textbf{Examples:}
\begin{lstlisting}
// Basic floating point types
type float digits 6 float32_t;        // At least 6 decimal digits
type float digits 15 float64_t;       // At least 15 decimal digits

// Constrained floating point types
type float digits 6 range -273.15 .. 1000.0 temperature_t;
type float digits 8 range 0.0 .. 100.0 percentage_t;
type float digits 10 range -180.0 .. 180.0 longitude_t;
type float digits 10 range -90.0 .. 90.0 latitude_t;

// Usage
temperature_t room_temp = 22.5;
percentage_t cpu_load = 87.3;
latitude_t current_lat = 37.7749;
longitude_t current_lon = -122.4194;
\end{lstlisting}

Floating point types are ideal for:
\begin{itemize}
\item Scientific computations requiring real numbers
\item Measurements with decimal precision
\item Geographic coordinates and spatial calculations
\item Physics simulations
\end{itemize}

\textbf{Note:} The actual precision depends on the target platform's floating point implementation. The \verb'digits' value specifies the minimum required precision.

\subsection{Fixed Point Types}

Fixed point types define real number types with exact decimal representation using a fixed delta value. They provide better precision than floating point for certain ranges and are deterministic.

\textbf{Ordinary Fixed Point Syntax:}
\begin{lstlisting}
type fixed delta <delta-value> range <min> .. <max> <type-name>;
\end{lstlisting}

The \verb'delta' specifies the smallest representable difference between values. All values are exact multiples of the delta.

\textbf{Examples:}
\begin{lstlisting}
// Ordinary fixed point types
type fixed delta 0.001 range 0.0 .. 5.0 voltage_t;      // mV precision
type fixed delta 0.01 range -100.0 .. 100.0 sensor_t;   // 10ms precision
type fixed delta 0.125 range 0.0 .. 1000.0 precise_t;   // 1/8 precision

// Usage
voltage_t supply_voltage = 3.300;  // Exactly 3.300V
sensor_t reading = 25.75;          // Exactly 25.75
precise_t measurement = 123.625;   // Exactly 123.625

// All operations maintain exact precision
voltage_t v1 = 1.500;
voltage_t v2 = 1.750;
voltage_t sum = v1 + v2;  // Exactly 3.250
\end{lstlisting}

\textbf{Decimal Fixed Point Syntax:}
\begin{lstlisting}
type decimal delta <delta-value> digits <precision> <type-name>;
\end{lstlisting}

Decimal fixed point types are specifically designed for financial calculations where exact decimal arithmetic is required.

\textbf{Examples:}
\begin{lstlisting}
// Decimal fixed point for financial applications
type decimal delta 0.01 digits 10 money_t;      // Pennies, up to 99999999.99
type decimal delta 0.001 digits 12 price_t;     // Mils precision
type decimal delta 0.0001 digits 8 interest_t;  // Basis points

// Usage
money_t account_balance = 1234.56;
money_t transaction = 42.99;
account_balance = account_balance + transaction;  // Exactly 1277.55

price_t stock_price = 123.456;
interest_t rate = 0.0325;  // 3.25%
\end{lstlisting}

Fixed point types are ideal for:
\begin{itemize}
\item Financial calculations requiring exact decimal arithmetic
\item Embedded systems with no floating point hardware
\item Control systems requiring deterministic behavior
\item Currency and monetary values
\item Sensor readings with known precision
\end{itemize}

\textbf{Key Differences:}
\begin{itemize}
\item \textbf{Ordinary fixed point:} Requires explicit range, optimized for specific value ranges
\item \textbf{Decimal fixed point:} Range derived from digits, optimized for decimal calculations
\item \textbf{Floating point:} Approximate representation, wider range, variable precision
\end{itemize}

\subsection{Subtypes}

Subtypes allow you to define constrained versions of existing types. A subtype is compatible with its base type but has additional range constraints. This is particularly useful for creating semantically meaningful types that share the same underlying representation.

\textbf{Syntax:}
\begin{lstlisting}
subtype <base-type> range <min-expr> .. <max-expr> <subtype-name>;
\end{lstlisting}

\textbf{Examples:}
\begin{lstlisting}
// Define base signed integer type
type range -2147483648 .. 2147483647 int_t;

// Natural numbers as a subtype of int_t (non-negative integers)
subtype int_t range 0 .. 2147483647 natural_t;

// Positive numbers as a subtype of int_t
subtype int_t range 1 .. 2147483647 positive_t;

// Percentage as a subtype of natural_t
subtype natural_t range 0 .. 100 percentage_t;

// Usage
int_t temperature = -10;      // Can be negative
natural_t count = 42;          // Cannot be negative
positive_t items = 1;          // Must be at least 1
percentage_t progress = 75;    // Limited to 0..100

// Subtype values are compatible with base type
int_t x = count;               // OK: natural_t is a subtype of int_t
natural_t y = temperature;     // Runtime check: may fail if negative
\end{lstlisting}

Key characteristics:
\begin{itemize}
\item Subtypes are compatible with their base type
\item Values can be assigned between base type and subtype (with runtime checks)
\item Subtypes inherit operations from their base type
\item Subtype ranges must be within the base type's range
\item Subtypes can be derived from other subtypes (transitive relationship)
\end{itemize}

\subsection{Structure Types}
\begin{lstlisting}
type range -1000 .. 1000 coordinate_t;
type struct {
  coordinate_t x;
  coordinate_t y;
} point_t;

type range 0 .. 150 age_t;
type struct {
  char* name;
  age_t age;
  bool is_employed;
} person_t;

person_t p;
p.name = "Alice";
p.age = 30;
p.is_employed = true;
\end{lstlisting}

\subsection{Structure Types with Type Invariants}

Type invariants specify constraints that must always hold for instances of a type:

\begin{lstlisting}
type range -1000 .. 1000 coordinate_t;
type struct {
  coordinate_t x;
  coordinate_t y;
} point_t [[type_invariant(x * x + y * y <= 1000000)]];

// This ensures all point_t values satisfy the distance constraint
// from origin: sqrt(x^2 + y^2) <= 1000
\end{lstlisting}

\begin{lstlisting}

type union {
  int_t int_value;
  char* string_value;
  bool bool_value;
} value_t;
\end{lstlisting}

\begin{lstlisting}
type enum {

  yellow = 20

color_t my_color = red;
\end{lstlisting}

\subsection{Bit Fields and Memory-Mapped I/O Registers}

\emph{stC} supports precise bit-level layout control for struct fields using Ada/SPARK-style representation clauses. This feature is essential for embedded systems programming, particularly for Memory-Mapped I/O (MMIO) register definitions where exact hardware layout must be specified.

\subsubsection{Field-Level Bit Attributes}

Field attributes specify the exact byte offset and bit position for each struct field using \verb'[[offset(...)]]' combined with \verb'bit(...)' or \verb'bits(...)':

\begin{lstlisting}
type modular 1 << 8 uint8_t;

type struct {
  bool enable [[offset(0) bit(0)]];
  bool interrupt_enable [[offset(0) bit(1)]];
  uint8_t mode [[offset(0) bits(2..4)]];      // 3 bits
  uint8_t reserved [[offset(0) bits(5..7)]];  // 3 bits
} control_reg_t [[packed]];
\end{lstlisting}

\textbf{Attribute Syntax:}
\begin{itemize}
\item \verb'[[offset(N) bit(M)]]' -- Field at byte N, single bit M (for booleans)
\item \verb'[[offset(N) bits(M..P)]]' -- Field at byte N, bits M through P (for multi-bit fields)
\item \verb'[[volatile]]' -- Field represents hardware register (suppress optimization)
\end{itemize}

\textbf{Important Rules:}
\begin{itemize}
\item \verb'offset' is \textbf{required} when using \verb'bit' or \verb'bits' (avoids C bit field ambiguity)
\item Either \textbf{all} fields in a struct have explicit \verb'[[offset(...)]]' attributes or \textbf{none} do
\item No mixing of explicit and implicit layout in the same struct
\item \textbf{Struct WITHOUT offset/bits attributes:} uses C layout (compiler applies normal struct packing rules)
\item \textbf{Struct WITH offset/bits attributes:} uses explicit Ada representation (programmer controls every bit position)
\end{itemize}

\subsubsection{Type-Level Attributes}

Type attributes apply to the entire struct:

\begin{itemize}
\item \verb'[[packed]]' -- No padding between fields, minimal size
\item \verb'[[at(address)]]' -- Map type to specific memory address (for MMIO)
\item \verb'[[volatile]]' -- All fields are volatile (hardware registers)
\end{itemize}

\subsubsection{Complete MMIO Register Example}

Example of a 32-bit GPIO control register:

\begin{lstlisting}
type modular 1 << 32 uint32_t;
type range 0 .. 7 uint3_t;
type range 0 .. 15 uint4_t;
type range 0 .. 255 uint8_t;

// GPIO Control Register (32-bit at 0x40000000)
type struct {
  bool port_enable [[offset(0) bit(0)]];       // Bit 0
  bool output_enable [[offset(0) bit(1)]];     // Bit 1
  bool pull_up [[offset(0) bit(2)]];           // Bit 2
  bool pull_down [[offset(0) bit(3)]];         // Bit 3
  uint4_t drive_strength [[offset(0) bits(4..7)]];  // Bits 4-7
  uint8_t reserved1 [[offset(1) bits(0..7)]];  // Bits 8-15
  uint8_t pin_value [[offset(2) bits(0..7)]];  // Bits 16-23
  uint8_t reserved2 [[offset(3) bits(0..7)]];  // Bits 24-31
} gpio_control_t [[packed]] [[at(0x40000000)]] [[volatile]];

// Access the memory-mapped register
void gpio_init() {
  gpio_control_t* gpio = 0x40000000;
  gpio->port_enable = true;
  gpio->output_enable = true;
  gpio->drive_strength = 7;  // Maximum drive strength
  gpio->pull_up = false;
  gpio->pull_down = false;
}
\end{lstlisting}

\subsection{Attributes and Aspects}

In \emph{stC}, C23-style attributes (using \verb'[[...]]' syntax) are the mechanism for specifying aspects, similar to Ada/SPARK aspects. This includes:
\begin{itemize}
\item \textbf{Function contracts}: \verb'[[pre(...)]]', \verb'[[post(...)]]', \verb'[[global(reads/writes => (...))]]'
\item \textbf{Function attributes}: \verb'[[no_return]]'
\item \textbf{Loop contracts}: \verb'[[loop_invariant(...)]]', \verb'[[loop_variant(...)]]'
\item \textbf{Type attributes}: \verb'[[type_invariant(...)]]', \verb'[[packed]]', \verb'[[at(...)]]'
\item \textbf{Variable attributes}: \verb'[[at(...)]]'
\end{itemize}

The \verb'[[...]]' syntax provides a familiar C-like notation while enabling the same level of specification and verification found in Ada/SPARK.

\subsection{Simple Function}
\begin{lstlisting}
int_t add(in int_t a, in int_t b) {

}
\end{lstlisting}

\subsection{Function with Contracts}

Contracts in \emph{stC} use C23-style attribute syntax with double square brackets \verb'[[...]]'. This is \emph{stC}'s way of implementing aspects, similar to SPARK contracts.

\begin{lstlisting}
type range -2147483648 .. 2147483647 int_t;
subtype int_t range 0 .. 2147483647 natural_t;

{
  return a / b;
}
\end{lstlisting}

\subsection{Function with Global-Effect Contracts}

Global-effect contracts specify which global variables a function reads or writes, similar to SPARK's \verb'Global' aspect:

\begin{lstlisting}
type modular 1 << 32 uint32_t;

uint32_t increment_counter()
  [[global(reads => (global_counter), writes => (global_sum))]]
  [[pre(global_counter < 1000)]]
  [[post(global_sum > 0)]]
{
  global_sum = global_sum + global_counter;
  return global_sum;
}

// Function that only reads globals (no writes)

  [[global(reads => (global_counter, global_sum))]]
{
  return global_counter + global_sum;
}
\end{lstlisting}

\section{Identifier Attributes}

\emph{stC} supports SPARK-style identifier attributes using the apostrophe operator. These attributes provide type and array information at compile time:

\subsection{Range Type Attributes}

\begin{lstlisting}
type range 0 .. 99 index_t;
type modular 100 array_100_t[100];

uint32_t process_array(array_100_t arr) {
  uint32_t sum;
  index_t i;

  sum = 0;

  // 'first gives the first valid index value
  i = index_t'first;

  // 'last gives the last valid index value
  while (i <= index_t'last) {
    sum = sum + arr[i];
    i = i + 1;
  }

  return sum;
}
\end{lstlisting}

\subsection{Array Attributes}

Like Ada/SPARK, identifier attributes also work with arrays to query their index ranges and length:

\begin{lstlisting}
type range 0 .. 99 index_t;
type modular 256 byte_t;

byte_t buffer[50];

void process_buffer() {
  // For arrays, 'first returns the first index
  index_t first_idx = buffer'first;   // Returns 0

  // For arrays, 'last returns the last index
  index_t last_idx = buffer'last;     // Returns 49

  // For arrays, 'length returns the number of elements
  index_t len = buffer'length;        // Returns 50

  // For arrays, 'range returns the index range
  for (index_t i in buffer'range) {
    buffer[i] = 0;
  }
}
\end{lstlisting}

\subsection{Available Attributes}

\begin{itemize}
\item \verb'identifier'first' -- For range types: returns the first value of the range. For arrays: returns the first index
\item \verb'identifier'last' -- For range types: returns the last value of the range. For arrays: returns the last index
\item \verb'identifier'length' -- For arrays: returns the number of elements (equivalent to \verb'last - first + 1')
\item \verb'identifier'range' -- For range types: returns the full range. For arrays: returns the index range
\item \verb'identifier'size' -- Returns the size in bytes
\end{itemize}

\section{Sizeof Operator}

The \verb'sizeof' operator returns the size in bytes of a type or expression, similar to C:

\begin{lstlisting}
type range 0 .. 255 byte_t;

  byte_t y;
} point_t;

// sizeof with type name

\section{Function Signature Types}

A \emph{function signature type} names the signature (parameters and return type) of a
function. Variables and parameters of a function signature type hold a reference to a
callable function; the compiler passes them by reference implicitly --- no explicit
pointer syntax is required.

\begin{lstlisting}
type range -2147483648 .. 2147483647 int_t;

// Declare a function signature type with no parameters, returning void
type void timer_cb_t();

// Declare a function signature type with parameters, returning void
type void binary_op_cb_t(in int_t a, in int_t b);

// Declare a function signature type returning a value
type int_t int_transform_t(in int_t x);

// Use as a parameter -- the compiler passes the function reference implicitly
void register_timer(in timer_cb_t callback, in uint32_t period_ms);

// Assign a named function to a function-signature-type variable
void my_handler() { }
timer_cb_t cb = my_handler;

// Call through the variable like a normal function
cb();

// Pass directly as an argument
register_timer(my_handler, 100);
\end{lstlisting}

\section{Child Modules}

A \emph{public} child module is visible to any module that imports it.
It inherits the public and private declarations of all its ancestor modules.

\begin{lstlisting}
// File: geometry.circle.stc
module geometry.circle {

  // Inherits point_t and coordinate_t from parent module geometry

  type range 0 .. 1000 radius_t;

  type struct {
    point_t center;
    radius_t radius;
  } circle_t;

  bool point_in_circle(in point_t p, in circle_t c) {
    return distance_squared(p, c.center) <= square(c.radius);
  }

}
\end{lstlisting}

\subsection{Private Child Modules}

A \emph{private} child module is prefixed with the \verb'private' keyword.
It can only be imported by its parent module and by sibling modules within
the same module family.  Unrelated modules cannot import it.
This corresponds directly to Ada's \emph{private child package}.

\begin{lstlisting}
// File: geometry.internal.stc
// Private child -- only geometry and geometry.* siblings can import this
private module geometry.internal {

  // Inherits point_t and coordinate_t from parent module geometry

  // Internal helper not exposed to users of the geometry module family
  coordinate_t clamp(in coordinate_t v,
                     in coordinate_t lo,
                     in coordinate_t hi) {
    if (v < lo) return lo;
    if (v > hi) return hi;
    return v;
  }

}
\end{lstlisting}

\begin{lstlisting}
// File: geometry.circle.stc  (sibling -- allowed to import the private child)
private import geometry.internal;   // private: only used in implementation

module geometry.circle {

  type range 0 .. 1000 radius_t;

  coordinate_t clamped_x(in point_t p, in coordinate_t lo, in coordinate_t hi) {
    return geometry.internal.clamp(p.x, lo, hi);
  }

}
\end{lstlisting}

\begin{lstlisting}
// File: app.stc  (unrelated module -- NOT allowed to import the private child)
import geometry.circle;    // OK: public child
// import geometry.internal;  // ERROR: private child, not accessible here

module app {

}
\end{lstlisting}

\subsection{Private Imports}

A \verb'private import' restricts an imported module to the private section of the importing
module.  It is analogous to Ada's \verb'private with' clause and is useful when an import
is an implementation detail that should not leak into the public interface.

\begin{lstlisting}
// File: board.stc
import cpu;                    // public: cpu types appear in the public interface
private import cpu.multicore;  // private: only used in the implementation

module board {

  const cpu.cpu_model_t cpu_model = cpu.cortex_a72;  // OK: cpu is public

  void start_secondary_cpu(in cpu.secondary_cpu_core_id_t cpu_id,
                           in cpu.address_t entry_point_address);

  private

  void start_core_impl() {
    // OK: cpu.multicore is accessible here (private section)
    cpu.multicore.wake(0);
  }

}
\end{lstlisting}

\subsection{Parent--Child Module Resolution}

Name resolution between a parent module and its child modules is \emph{bidirectional}
and \emph{automatic}---no \verb'import' statement is required in either direction.

\begin{itemize}
\item \textbf{Child to parent} (already covered above): a child module inherits all
      public and private declarations of its ancestor modules and can use them
      without an \verb'import'.
\item \textbf{Parent to child}: a parent module can reference the public declarations
      of any of its direct child modules by using the fully qualified name
      (e.g.\ \verb'logger.output.write_line(...)') without importing the child.
\item \textbf{Sibling modules}: sibling child modules (children of the same parent)
      must use an explicit \verb'import' to access each other's declarations.
\item \textbf{Unrelated modules}: modules that are not in the same parent--child
      hierarchy must use an explicit \verb'import'.
\end{itemize}

The compiler implements this through two-pass resolution:
\begin{enumerate}
\item \textbf{First pass}: scan all modules and extract their public interfaces
      (types, function signatures, constants).
\item \textbf{Second pass}: resolve all names across the module tree and compile
      function bodies.
\end{enumerate}

This design eliminates the circular dependency that would arise if the parent had to
\verb'import' its child while the child simultaneously depends on the parent.
In Ada, this circularity is avoided because the parent \emph{specification} does not
depend on the child---only the parent \emph{body} does, and bodies are compiled after
all specifications.  Since \emph{stC} does not separate specification and body,
bidirectional parent--child resolution achieves the same effect without requiring
two files per module.

\textbf{Example --- parent module (\texttt{logger.stc}):}

\begin{lstlisting}
// File: logger.stc
// No import needed for child modules logger.output or logger.formatting
import uart;

module logger {

  type enum { debug = 0, info = 1, error = 2 } log_level_t;

  void put_char(in char c) {
    uart.send(c);
  }

  void print_string(in char[] s) {
    for (type range 0 .. 65535 uint16_t i in s'range) {
      put_char(s[i]);
    }
  }

  // References child module logger.output -- no import needed
  void system_error(in char[] msg)
    [[no_return]]
  {
    logger.output.write_line(error, msg);
    print_string("*** System halted ***\n");
  }

}
\end{lstlisting}

\textbf{Example --- child module (\texttt{logger.output.stc}):}

\begin{lstlisting}
// File: logger.output.stc
// No import needed for parent module logger

module logger.output {

  // Inherits log_level_t, put_char, print_string from parent

  void write_line(in log_level_t level, in char[] msg) {
    // Uses parent's print_string -- no import needed
    if (level == error) {
      print_string("ERROR: ");
    } else if (level == info) {
      print_string("INFO: ");
    } else {
      print_string("DEBUG: ");
    }
    print_string(msg);
    put_char('\n');
  }

}
\end{lstlisting}

\textbf{Example --- sibling child module (\texttt{logger.formatting.stc}):}

\begin{lstlisting}
// File: logger.formatting.stc
// No import needed for parent module logger (automatic)
// Explicit import needed for sibling module logger.output
import logger.output;

module logger.formatting {

  // Inherits log_level_t, print_string from parent (automatic)

  void log_key_value(in log_level_t level,
                     in char[] key,
                     in char[] value) {
    print_string(key);        // parent declaration (automatic)
    print_string(": ");
    // Sibling declaration (requires import above)
    logger.output.write_line(level, value);
  }

}
\end{lstlisting}

\textbf{Summary of resolution rules:}

\begin{center}
\begin{tabular}{lll}
\textbf{Relationship} & \textbf{Import needed?} & \textbf{Example} \\
\hline
Child $\to$ Parent & No (automatic) & \verb'logger.output' uses \verb'print_string' \\
Parent $\to$ Child & No (automatic) & \verb'logger' uses \verb'logger.output.write_line' \\
Sibling $\to$ Sibling & Yes & \verb'logger.formatting' imports \verb'logger.output' \\
Unrelated & Yes & \verb'logger' imports \verb'uart' \\
\end{tabular}
\end{center}

\section{Compile-Time Conditionals}
The \verb'compile_if' statement allows for conditional compilation based on constant expressions evaluated at compile time. This is useful for platform-specific code or conditional features.

\subsection{Platform-Specific Types}
\begin{lstlisting}
module platform_types {

  // Define types based on platform word size
  compile_if machine_width == 64 {
    type range 0 .. (1 << 63) - 1 unsigned_long_t;
    type range -(1 << 63) .. (1 << 63) - 1 signed_long_t;
  } else {
    type range 0 .. (1 << 31) - 1 unsigned_long_t;
    type range -(1 << 31) .. (1 << 31) - 1 signed_long_t;
  }

  // Use underscores for readability in large numbers
  compile_if machine_width >= 32 {
    type modular 0x1_0000_0000 uint32_t;  // 4 billion
  }

}
\end{lstlisting}

\subsection{Numeric Literal Separators}
Both underscores and apostrophes can be used as digit separators in numeric literals to improve readability. Apostrophes are supported for compatibility with C.
\begin{lstlisting}
module numeric_separators {

  // Underscore separators
  type range 0 .. 1_000_000 million_t;
  type modular 0x8000_0000 half_uint32_t;
  type modular 0b1111_1111 byte_mask_t;

  // Apostrophe separators (for C compatibility)
  type range 0 .. 1'000'000 million_alt_t;
  type modular 0xDEAD'BEEF hex_value_t;

  // Note: A literal must use only one separator style
  // type modular 0x8000_0'000 invalid_t;  // Error: mixed separators

}

\section{Depends Contracts}
Information-flow contracts specify which outputs depend on which inputs, enabling
formal verification of data-flow properties.  This maps directly to SPARK's
\verb'Depends' aspect.

\begin{lstlisting}
module depends_example {

  // swap: each output depends on both inputs.
  // x => (x, y) is stC's way of expressing SPARK's x =>+ y
  // (output depends on inputs AND its own initial value).
  void swap(inout int32_t x, inout int32_t y)
    [[depends(x => (x, y), y => (x, y))]]
  {
    int32_t tmp = x;
    x = y;
    y = tmp;
  }

  // clear: result is independent of all inputs
  void clear(out int32_t result)
    [[depends(result => void)]]
  {
    result = 0;
  }

  // copy: dst depends solely on src
  void copy(out int32_t dst, in int32_t src)
    [[depends(dst => src)]]
  {
    dst = src;
  }

}
\end{lstlisting}

\textbf{Note:} SPARK's \verb'=>+' syntax (\emph{``output depends on inputs and on its
own prior value''}) is expressed in \emph{stC} by including the output variable in its
own input list.  For example, \verb'x => (x, y)' is equivalent to SPARK's
\verb'x =>+ y'.  The explicit form is preferred because it is unambiguous and
familiar to C programmers.

\section{Abstract State and Refined State}
Large modules can hide their internal variables behind an abstract state name,
enabling callers to write information-flow contracts at the module interface
level without knowing the concrete implementation variables.  This maps to
SPARK's \verb'Abstract_State' and \verb'Refined_State' aspects.

\begin{lstlisting}
module Server [[abstract_state(State)]] {

  // Public interface refers only to the abstract state name.
  void init()   [[global(writes => (State))]] {}
  void push(in uint8_t val)
               [[global(writes => (State))]] {}
  uint32_t count()
               [[global(reads => (State))]]  { return 0; }

  private

  // Private variables are tagged with the abstract state they refine.
  uint8_t  buffer[64] [[refined_state(State)]];
  uint32_t head       [[refined_state(State)]];
  uint32_t tail       [[refined_state(State)]];

}
\end{lstlisting}

\section{Generic Modules}
\emph{stC} supports parameterised modules using C-style generic formal parameter
syntax.  Generics are instantiated via \verb'import' with named actual
parameters.

\subsection{Type and Function Formals}

\begin{lstlisting}
generic(type T, bool less_than(in T a, in T b))
module Sort_Utils {

  void sort(inout T arr[], in uint32_t len) {}
  bool is_sorted(in T arr[], in uint32_t len) { return true; }

}
\end{lstlisting}

Instantiate with named actual parameters using \verb'=>':

\begin{lstlisting}
import Sort_Utils(T => int32_t, less_than => int32_less) as Int_Sort;
\end{lstlisting}

\subsection{Type and Const Formals}

\begin{lstlisting}
generic(type T, const uint32_t Capacity)
module Fixed_Queue {

  type struct {
    T items[Capacity];
    uint32_t head;
    uint32_t tail;

<module> ::=
   (("private")? "import" <module-name> (<generic-actual-part>)?
      ("as" <module-identifier>)? ";")*
   (<generic-formal-part>)?
   ("private")? "module" <module-name> (<module-attributes>)? "{"
   <declaration>*
   ("private" <declaration>+)? "}"

<generic-formal-part> ::=
   "generic" "(" <generic-formal-parameter> ("," <generic-formal-parameter>)* ")"

<generic-formal-parameter> ::=
   "type" <type-identifier> |
   "const" <type-identifier> <constant-identifier> |
   <type-identifier> <function-identifier>
      "(" (<param-declaration> ("," <param-declaration>)*)? ")"

<function-identifier> ::= "<identifier>"

<generic-actual-part> ::=
   "(" <generic-actual-parameter> ("," <generic-actual-parameter>)* ")"

<generic-actual-parameter> ::=
   "<identifier>" "=>" ("<identifier>" | <constant-expression>)

<module-attributes> ::= ("[[" <module-attribute> "]]")+

<module-attribute> ::=

<module-name> ::= "<identifier>" ("." "<identifier>")*

<module-identifier> ::= "<identifier>"

<declaration> ::=
   <constant-declaration> |
   <type-declaration> |

   <global-variable-declaration> |
   <function-declaration> |
   <extern-variable-declaration> |
   <extern-function-declaration> |
   <compile-if-declaration>

<constant-declaration> ::=
   "const" <type-identifier> <constant-declarator> "=" <constant-expression> ";" |
   "const" "type" <type-declarator> <type-identifier> <constant-identifier>
      "=" <constant-expression> ";"

<constant-declarator> ::=
   ("*")? <constant-identifier>
             ("[" "]" ("[" <constant-integer-expression> "]")* |
              "[" <constant-integer-expression> "]")*

<constant-identifier> ::= "<identifier>"

<type-declaration> ::=
   "type" <type-declarator> <type-identifier> (<type-attributes>)? ";"

<function-sig-type-declaration> ::=
   "type" (<return-type-identifier> | "void") <type-identifier>
   "(" (<param-declaration> ("," <param-declaration>)*)? ")" ";"

<return-type-identifier> ::= <type-identifier>

<subtype-declaration> ::=
   "subtype" <type-identifier> "range" <constant-integer-expression>
      ".." <constant-integer-expression> <subtype-identifier>
      (<type-attributes>)? ";"

<type-identifier> ::= "<identifier>" ("." "<identifier>")*

<subtype-identifier> ::= "<identifier>"

<type-declarator> ::=
   "range" <constant-integer-expression> ".." <constant-integer-expression> |
   "modular" <constant-integer-expression> |
   "float" "digits" <constant-integer-expression>
      ("range" <constant-expression> ".." <constant-expression>)? |
   "fixed" "delta" <constant-expression> "range"
      <constant-expression> ".." <constant-expression> |
   "decimal" "delta" <constant-expression> "digits" <constant-integer-expression> |
   ("struct" | "union") "{" (<struct-field-declaration> ";")+ "}" |
   "enum" "{" <enum-entry> ("," <enum-entry>)* "}"

<struct-field-declaration> ::=
   <type-identifier> <struct-field-declarator>
      (<field-attributes>)? ("=" <constant-expression>)?

<struct-field-declarator> ::=
   ("*")? <struct-field-identifier>
            ("[" <constant-integer-expression> "]")*

<struct-field-identifier> ::= "<identifier>"

<field-attributes> ::=
   ("[[" <field-attribute> "]]")+

<field-attribute> ::=
   "offset" "(" <constant-integer-expression> ")"
      ("bit" "(" <constant-integer-expression> ")" |
       "bits" "(" <constant-integer-expression> ".." <constant-integer-expression> ")") |
   "volatile"

<enum-entry> ::=
   <enum-entry-identifier> ("=" <constant-integer-expression>)?

<enum-entry-identifier> ::= "<identifier>"

<global-variable-declaration> ::=
   ("const" | "volatile")? <type-identifier> <global-variable-declarator>
   ("=" <constant-expression>)? (<variable-attributes>)? ";"

<global-variable-declarator> ::=
   ("*")? <global-variable-identifier>
            ("[" <constant-integer-expression> "]")*

<global-variable-identifier> ::= "<identifier>"

<function-declaration> ::=
   ("void" | <type-identifier> ("*")?) <function-identifier>
       "(" (<param-declaration> ("," <param-declaration>)*)? ")"
       (<function-attributes>)?
       <statement-block>

<statement-block> ::=
      "{" (<local-variable-declaration> | <statement>)* "}"

<local-variable-declaration> ::=
   ("volatile")? <type-identifier> <local-variable-declarator>
   ("=" <expression>)? (<variable-attributes>)? ";"

<local-variable-declarator> ::=
   ("*")? <local-variable-identifier> ("[" <index-expression> "]")*

<local-variable-identifier> ::= "<identifier>"

<statement> ::=
    <assignment> |
    <void-function-call> |
    <if-statement> |
    <while-statement> |
    <for-statement> |
    <do-while-statement> |
    <switch-statement> |
    <statement-block> |
    <return-statement> |
    <compile-if-statement>

<assignment> ::= <variable-reference> "=" <expression>

<void-function-call> ::= <void-function-reference>  "(" (<function-call-argument> ("," <function-call-argument>)*)? ")"

<void-function-reference> ::=
  <void-function-identifier> |
  <void-function-pointer-expression>

<if-statement> ::= "if" "(" <boolean-expression> ")" <statement-block> ("else" <statement-block>)?

<while-statement> ::= "while" "(" <boolean-expression> ")" (<loop-attributes>)? <statement-block>

<do-while-statement> ::= "do" <statement-block> "while" "(" <boolean-expression> ")" ";"

<for-statement> ::=
   "for" "(" (<local-variable-declaration> | <assignment>)? ";"
   <boolean-expression>? ";"
   <assignment>? ")" (<loop-attributes>)? <statement-block> |
   "for" "(" <type-identifier> <local-variable-identifier> "in" <expression> ")"
   (<loop-attributes>)? <statement-block>

<switch-statement> ::=
   "switch" "(" <expression> ")" "{"
   <switch-case>*
   (<default-case>)?
   "}"

<switch-case> ::= "case" <constant-expression> ":" <statement>*

<default-case> ::= "default" ":" <statement>*

<return-statement> ::= "return" (<expression>)? ";"

<compile-if-statement> ::=
   "compile_if" <constant-expression> "{"
      <statement>*
   "}" ("else" "{" <statement>* "}")?

<compile-if-declaration> ::=
   "compile_if" <constant-expression> "{"
      <declaration>*
   "}" ("else" "{" <declaration>* "}")?

<param-declaration> ::=
   (<parameter-mode>)? <type-identifier> <param-declarator>

<parameter-mode> ::= "in" | "out" | "inout"

<param-declarator> ::=
   ("*")? <param-identifier> ("[" "]" ("[" <constant-integer-expression> "]")*)?

<param-identifier> ::= "<identifier>"

<function-call-argument> ::= <expression>

<extern-variable-declaration> ::=
   "extern" ("const")? <type-identifier> <global-variable-declarator> ";"

<extern-function-declaration> ::=
   "extern" ("void" | <type-identifier> ("*")?) <function-identifier>
   "(" (<param-declaration> ("," <param-declaration>)*)? ")" ";"

<expression> ::= <ternary-expression>

<ternary-expression> ::=
   <logical-or-expression> ("?" <expression> ":" <expression>)?

<logical-or-expression> ::=
   <logical-and-expression> ("||" <logical-and-expression>)*

<logical-and-expression> ::=
   <bitwise-or-expression> ("&&" <bitwise-or-expression>)*

<bitwise-or-expression> ::=
   <bitwise-xor-expression> ("|" <bitwise-xor-expression>)*

<bitwise-xor-expression> ::=
   <bitwise-and-expression> ("^" <bitwise-and-expression>)*

<bitwise-and-expression> ::=
   <equality-expression> ("&" <equality-expression>)*

<equality-expression> ::=
   <relational-expression> (("==" | "!=" | "in") <relational-expression>)*

<relational-expression> ::=
   <shift-expression> (("<" | ">" | "<=" | ">=" | "..") <shift-expression>)*

<shift-expression> ::=
   <additive-expression> (("<<" | ">>") <additive-expression>)*

<additive-expression> ::=
   <multiplicative-expression> (("+" | "-") <multiplicative-expression>)*

<multiplicative-expression> ::=
   <power-expression> (("*" | "/" | "%") <power-expression>)*

<power-expression> ::=
   <unary-expression> ("**" <unary-expression>)*

<unary-expression> ::=
   <postfix-expression> |
   <unary-operator> <unary-expression> |
   "sizeof" "(" (<type-identifier> | <expression>) ")"

<unary-operator> ::= "+" | "-" | "!" | "~" | "*" | "&"

<postfix-expression> ::=
   <primary-expression>
      (("[" <expression> "]") |
       ("(" (<function-call-argument> ("," <function-call-argument>)*)? ")") |
       ("." <struct-field-identifier>) |
       ("->" <struct-field-identifier>) |
       ("'" <identifier-attribute>))*

<identifier-attribute> ::= "first" | "last" | "length" | "range" | "size"

<primary-expression> ::=
   <identifier> |
   <literal> |
   "(" <expression> ")" |
   <type-cast-expression> |
   "{" <expression> ("," <expression>)* "}"

<type-cast-expression> ::= <type-identifier> "(" <expression> ")"

<boolean-expression> ::= <expression>

<index-expression> ::= <expression>

<constant-expression> ::= <expression>

<constant-integer-expression> ::=
   "<binary-integer-literal>" |
   "<decimal-integer-literal>" |
   "<hexadecimal-integer-literal>" |
   <constant-identifier> |
   <integer-unary-op> <constant-integer-expression> |
   <constant-integer-expression> <integer-binary-op>
      <constant-integer-expression>

<integer-unary-op> ::= "+" | "-" | "~"

<integer-binary-op> ::=
   "+" | "-" | "*" | "/" | "%" | "**" | "<<" | ">>" |
   "&" | "|" | "^"

<literal> ::=
   "<binary-integer-literal>" |
   "<decimal-integer-literal>" |
   "<hexadecimal-integer-literal>" |
   "<floating-point-literal>" |
   "<character-literal>" |
   "<string-literal>" |
   "<boolean-literal>"

<boolean-literal> ::= "true" | "false"

<variable-reference> ::=
  <variable-identifier> ("." <struct-field-identifier> ("[" <index-expression> "]")*)* |
  <variable-identifier> ("[" <index-expression> "]")*

<variable-identifier> ::= "<identifier>"

<void-function-identifier> ::= "<identifier>"

<variable-attributes> ::=
   ("[[" <variable-attribute> "]]")+

<variable-attribute> ::=
   "at" "(" <constant-expression> ")" |
   "refined_state" "(" "<identifier>" ")"

<function-attributes> ::=
   <function-attribute>+

<function-attribute> ::=
   "[[" (<function-contract> | "no_return") "]]"

<function-contract> ::=
   <precondition> | <postcondition> | <global-clause> | <depends-clause>

<depends-clause> ::=
   "depends" "(" <depends-item> ("," <depends-item>)* ")"

<depends-item> ::=
   <depends-output> "=>" <depends-rhs>

<depends-output> ::=
   "<identifier>" | "(" "<identifier>" ("," "<identifier>")* ")"

<depends-rhs> ::=
   "void" | "<identifier>" | "(" "<identifier>" ("," "<identifier>")* ")"

<precondition> ::= "pre" "(" <boolean-expression> ")"

<postcondition> ::= "post" "(" <boolean-expression> ")"

<global-clause> ::=
   "global" "(" <global-effect> ("," <global-effect>)* ")"

<global-effect> ::=
   ("reads" | "writes") "=>" "(" <identifier> ("," <identifier>)* ")"

<loop-attributes> ::=
   <loop-attribute>+

<loop-attribute> ::=
   "[[" <loop-contract> "]]"

<loop-contract> ::=
   <loop-invariant> | <loop-variant>

<loop-invariant> ::= "loop_invariant" "(" <boolean-expression> ")"

<loop-variant> ::= "loop_variant" "(" <expression> ")"

<type-attributes> ::=
   ("[[" <type-attribute> "]]")+

<type-attribute> ::=
   "packed" | "at" "(" <constant-expression> ")" |
   "type_invariant" "(" <boolean-expression> ")"
